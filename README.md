# 동해선 PSD 교체주기 예측

동해선 스크린도어(PSD) 부품의 권장 교체주기를 날씨(기상청 AWS 2022~2025년치, 역마다 가장
가까운 지점 7곳)로 보정해 계산하고, 역 → 문 → 부품 단위로 보여 주는 도구다. 현장의 정비기록
엑셀을 원본으로 두고, 올리면 DB를 그 엑셀에 맞춰 교체주기에 반영한다(없으면 더미데이터로 대신).
현재 상태는 엑셀·PDF 보고서로 내려받을 수 있다.

- 설계 결정: [설계_v2.md](설계_v2.md)
- 계산 공식 근거: [4단계_계산공식_근거조사.md](4단계_계산공식_근거조사.md)
- 진행 상황: [MVP_계획.md](MVP_계획.md)
- 화면 방향성(가정 날씨로 만든 참고용 목업, 실제 계산과는 다름): [목업/동해선_PSD_교체주기_목업.html](목업/동해선_PSD_교체주기_목업.html)

## 다른 컴퓨터에서 처음 설치하기

날씨 집계 결과(`data/processed/aws_weather_daily.csv`)는 저장소에 들어 있어서, 날씨를 다시 받지
않아도 아래 순서만 따라 하면 화면이 뜬다. Windows·macOS·Linux 어디서든 같다.

### 1. 준비물

- Python 3.10 이상
- MySQL 8.0 (서버가 켜져 있어야 함)
- Git

### 2. 내려받기와 패키지 설치

```bash
git clone https://github.com/kms8994/PSD_Predictive_Maintenance.git
cd PSD_Predictive_Maintenance
python -m venv .venv
```

가상환경 켜기 — Windows: `.venv\Scripts\activate`, macOS/Linux: `source .venv/bin/activate`

```bash
pip install -r requirements.txt
```

### 3. MySQL에 DB와 전용 계정 만들기

MySQL에 root로 접속해서(`mysql -u root -p`) 한 번만 실행한다. `<비밀번호>`는 직접 정한다:

```sql
CREATE DATABASE IF NOT EXISTS psd CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER IF NOT EXISTS 'psd_app'@'localhost' IDENTIFIED BY '<비밀번호>';
GRANT ALL PRIVILEGES ON psd.* TO 'psd_app'@'localhost';
FLUSH PRIVILEGES;
```

### 4. `.env` 만들기

`.env.example`을 복사해 `.env`로 저장하고 `DB_PASSWORD`에 3단계의 비밀번호를 넣는다.
`.env`는 비밀번호가 들어 있어 저장소에 올라가지 않는다(`.gitignore`).

```
DB_HOST=localhost
DB_PORT=3306
DB_NAME=psd
DB_USER=psd_app
DB_PASSWORD=<비밀번호>
```

### 5. 표 만들기와 교체주기 계산

```bash
python scripts/init_db.py          # 표 생성 + 역 24개·문 736개·부품 약 1만 개(소분류 34종) 등 기본 데이터
python scripts/compute_cycles.py   # 날씨로 역 x 장애부위 소분류 권장 교체주기를 계산해 저장
```

역 목록은 `data/stations/동해선_역목록.xlsx`(저장소에 있음)에서 읽는다 — 아래 "역 목록·역 환경 고치기".
**분류표 파일이 먼저 있어야 한다**(2026-11-24 v3, `데이터셋_v3_설계.md`). 예측 단위는 코레일 장애 이력 양식의 장애부위 소분류인데,
분류표가 코레일 자료라 저장소에 없다. 개발 PC의 `data/private/장애분류.json`을 USB 등으로 같은 자리에 복사한다(공개 저장소·메신저에
올리지 않는다). 없으면 공개 예시 `data/sample/장애분류_예시.json`(소분류 7개)으로 돌고, 화면 위 기준일 옆에 "예시 분류표"가 붙는다.
v2 DB(7종 부품)가 있는 PC는 `python scripts/init_db.py --reset`으로 새로 만든다(그냥 돌리면 멈추고 알려 준다).

### 6. (선택) 초기 데이터 넣기 — 더미 정비 기록

```bash
python scripts/generate_dummy_records.py --save   # data/private/dummy/에 더미·샘플·정답을 만든다(수십 초)
python scripts/load_initial_records.py
```

> **⚠️ 이 단계는 선택이다. 넣을지 말지에 따라 화면이 크게 달라진다.**
>
> 실제 고장 데이터가 아직 없어서, 장애부위마다 2022년부터 일생을 따라가며 사후조치·사전조치를 만든 더미 기록을 쓴다
> (코레일 장애 이력 양식과 같은 칸, 2026-11-24 기준 약 5,600건 + 시연용 샘플 두 달치 약 300건). 진짜 수명은 날씨 공식과 일부러
> 다르게 두었고 그 정답은 `data/private/dummy/정답_수명모수.json`에 따로 있다(앱은 읽지 않음, 보정이 맞는지 재는 데만 씀).
> 분류표로 만들어 결과도 비공개 폴더에 둔다. 만드는 방식은 `데이터셋_v3_설계.md` 7장.
>
> - **시연·발표처럼 화면을 채워 보여 주려면 넣는다.** 넣지 않으면 기록이 0건이라 부품이 거의 전부 "안전"이다.
> - **실제 고장 데이터를 받아서 처음부터 쓰려면 넣지 않는다.** 가짜 기록이 실제 데이터와 섞이면 교체주기 보정이 틀어진다.
>   실제 기록은 화면의 "교체 기록" 탭에서 현장의 장애 이력 엑셀을 그대로 올리면 된다.
> - 이미 기록이 있는 DB에서는 겹치지 않게 아무것도 하지 않는다. 더미만 든 개발 DB는 `--replace`로 기록·업로드 이력을 지우고
>   새 더미로 바꾼다. 넣은 뒤 빼고 싶으면 "교체 기록 → 업로드 이력"에서 되돌리거나 `init_db.py --reset`으로 다시 만든다.

### 6-1. (선택) AI 고장 위험도 모델 학습

```bash
python scripts/train_risk_model.py
```

DB의 정비 기록으로 첫 모델(v1)을 학습해 `models/risk_v1.joblib`에 저장하고, 버전 기록을 DB `risk_models` 표에 남긴다
(노트북에서 40초 안팎, 표가 없으면 만든다). 데스크탑에서 가상 노선 여러 벌로 미리 학습한 모델을 가져와 쓸 수도 있다 —
`데스크탑_작업_안내.md`. 모델 파일은 저장소에 없으니(`.gitignore`) 컴퓨터마다 한 번 돌린다. 그 뒤로는
정비기록을 올리거나 되돌릴 때마다 자동으로 다시 학습한다. 안 돌리면 현황의 "AI 고장 위험도" 칸에 학습 방법만 나온다.
자세한 건 아래 "AI 고장 위험도".

### 7. 실행

```bash
uvicorn psd.api:app --reload
```

브라우저에서 `http://127.0.0.1:8000/` 을 연다. API 문서는 `http://127.0.0.1:8000/docs`.

PDF 보고서의 한글 글꼴은 Windows의 맑은 고딕을 쓰고, 없으면(macOS·Linux) PDF 뷰어의 기본 한글 글꼴로
대신 나온다.

## 화면 구성

상태는 네 가지다: **교체 임박**(예정일까지 6개월 이하, 지난 경우 포함) · **확인 필요**(교체 기록 없이 예정일이 지남) ·
**주의**(1년 이하) · **안전**. 화면·엑셀 보고서·PDF 보고서가 같은 이름을 쓴다(2026-11-02에 "위험"을 "교체 임박"으로 바꿈 —
안전설비라 "위험"이 "지금 문이 위험하다"로 읽혔다). 교체 예정의 숫자는 모두 부품 수다.

| 탭 | 내용 |
| --- | --- |
| 현황 | 노선 전체 상태, 교체 예정 목록(전체 보기에서 기간·역·부품으로 거르기), AI 고장 위험도 상위 5개, 반복 고장 의심 문 |
| 역 | 역 목록(목록 / 역 x 부품 격자), 역 → 부품별 상태 표(“문 목록”으로 대상 문을 상태·예정일별로 보고 작업 지시용으로 복사) → 문 → 부품 상태, 그 역 보고서(엑셀·PDF). 현황에서 "문 N개" 줄을 누르면 그 문 목록이 펼쳐진 채로 열린다. 역 화면에 개통일과 PSD 설치일을 따로 보여 준다. 부품 화면은 쉬운 설명이 먼저 나오고, 계산식·원인별 비중·출처는 "계산 자세히"에 접혀 있다 |
| 교체 계획 | 기간마다 교체 예정 부품 수(12개월=월별, 3년=분기별, 5년=연도별, 맨 앞 칸은 이번 달·분기·해), 가장 몰리는 때, 부품별 표, 기간을 누르면 그때의 역별 물량(역마다 부품별 개수). "엑셀로 받기"는 부품별·역별·역 x 부품 시트. 예정 교체만 세므로, 돌발 고장 예비품 참고로 "지난 1년 고장" 수를 같이 보여 준다 |
| 교체 기록 | 정비기록 엑셀 올리기(먼저 비교 → 반영), 업로드 이력(올린 사람 포함)·되돌리기, 기록 찾기(역·부품·사유·조치·작업일 기간·쪽 넘기기), 전체 기록 엑셀로 받기 |
| AI 관리 | 고장 위험도 순위(역·부품으로 거르기), 지금 쓰는 모델의 검증 결과, 학습 이력·다시 학습, 가상 현장 결과 |

## 구성

```

                                                                        ↓
                                                          [주기 계산] psd/cycle.py
                                                                        ↓
정비기록 엑셀(원본) ─────┐                                                          MySQL
초기 데이터(선택) ───────┼──→ 비교·맞추기(psd/sync.py) → 주기 보정(psd/calibrate.py) ──┘
                          │
                   [API] psd/api.py (FastAPI) ──→ [화면] psd/web/ ──→ 엑셀·PDF 보고서
```

## 날씨 데이터 다시 받기 (보통은 필요 없음)

**AWS(실제 계산에 쓰는 것, 수동):** API허브 AWS 엔드포인트가 아직 미승인(403)이라, 기상자료
개방포털(data.kma.go.kr) 웹 화면에 무료 회원가입으로 로그인해 "방재기상관측(AWS) → 파일셋"
에서 시간 자료를 받아야 한다(자료형태=시간 자료, 지역=부산·울산, 기간은 필요한 만큼).
`data/raw/aws/hourly/`에 CSV를 모은 뒤:

```bash
python scripts/preprocess_aws_weather.py   # 시간→일 평균 집계 → data/processed/aws_weather_daily.csv
python scripts/compute_cycles.py           # 새 날씨로 주기 다시 계산
```

원본은 `data/raw/`(저장소에 올리지 않음), 집계 결과는 `data/processed/aws_weather_daily.csv`(저장소에 올림)에 있다.
예전에 쓰던 ASOS(부산·울산 2곳) 자동 수집 스크립트와 자료는 계산에 쓰지 않아 2026-11-01에 지웠다.

## DB 다시 만들기

역/부품 구성 자체를 바꿨다면 `python scripts/init_db.py --reset`으로 표를 지우고 다시 만든다(교체 기록도
모두 지워진다). 그다음 `compute_cycles.py`와, 필요하면 `load_initial_records.py`를 다시 실행한다.
`init_db.py`·`compute_cycles.py`는 여러 번 실행해도 안전하다(있으면 지우고 새로 넣음, 없는 컬럼은 자동으로 추가).

**이미 설치한 PC에서 코드를 새로 받았다면** `python scripts/init_db.py`를 한 번 실행한다. 2026-11-01에
추가된 업로드 이력 표(`upload_batches`)와 교체 기록의 `batch_id` 컬럼, 2026-11-02에 추가된 업로드 이력의 올린 사람
(`upload_batches.uploaded_by`) 컬럼이 만들어진다(기존 기록은 그대로). 이걸 안 하면 교체 기록 탭이 열리지 않는다.

## 역 목록·역 환경 고치기 (고정 파일)

노선은 **동해선 하나로 고정**이다(`psd/stations.py` `LINE_NAME`). 역 목록과 역 환경은 한 번 정하면 거의 안 바뀌어 업로드로 받지 않고
고정 엑셀 파일에 둔다(2026-11-24). 파일마다 '안내' 시트에 규칙, '변경 이력' 시트에 바꾼 기록을 적는다.

| 파일 | 공개 | 내용 |
| --- | --- | --- |
| `data/stations/동해선_역목록.xlsx` | 공개 | ID(영구 번호) · 순서(노선 순서) · 역 이름 · 옛 이름 · 개통일 · PSD 사용개시일 · AWS 지점 · 운영/개통 전 · 바다·하천 인접(추정) |
| `data/private/역환경.xlsx` | 비공개 | '항목' 시트에 카테고리·항목(값 종류 선택/숫자/글, 선택지)을 정하고 '역 환경' 시트에 역마다 값. 지금은 '구조'(역 구조·승강장 형태·외기 노출·구조 메모) |
| `data/sample/역환경_예시.xlsx` | 공개 | 위와 같은 틀, 값 없음(비공개 파일이 없을 때 읽음) |

**역 목록을 바꿀 때** — 먼저 보고, 그다음 반영한다:

```bash
python scripts/init_db.py --check   # 무엇이 바뀌는지만 본다(새 역·이름·순서·운영·사용개시일)
python scripts/init_db.py           # 반영
python scripts/compute_cycles.py    # 새 역을 더했거나 AWS 지점을 바꿨을 때
```

- **새 역**: 가장 큰 ID + 1로 한 줄 더하고, 노선 순서에 맞게 '순서'를 다시 매긴다. ID는 기록·문·부품을 묶는 번호라 절대 바꾸거나 다시 쓰지 않는다.
- **이름 변경**: '역 이름'을 새 이름으로 고치고 예전 이름을 '옛 이름'에 적는다. 예전 이름으로 적힌 정비기록도 같은 역으로 읽는다.
- **역을 없애기**: 지우지 말고 '개통 전'으로 둔다. 정비기록이 있는 역은 지우거나 '개통 전'으로 바꾸려 하면 `init_db.py`가 멈춘다.
- **PSD 사용개시일 변경**: 교체 기록이 없는 부품의 설치일이 새 날로 옮겨진다.
- 파일이 틀리면(ID·순서·이름 겹침, 모르는 AWS 지점, 날짜 오류) 앱과 스크립트가 시작할 때 무엇이 틀렸는지 알리고 멈춘다.

**역 환경을 바꿀 때** — 파일만 고치면 된다(서버를 다시 켤 필요 없음, 역 화면 '역 환경'에 보인다). 카테고리를 늘리려면 '항목' 시트에
한 줄 더하고 '역 환경' 시트에 같은 이름의 열을 더한다. 선택지에 없는 값·숫자가 아닌 값은 그 칸만 비우고 화면에 경고로 보인다.
지금은 표시만 하고 계산에는 쓰지 않는다(값이 다 차면 AI 특징 후보).

## 정비기록 올리기 (엑셀이 원본)

현장은 정비기록을 엑셀로 관리하므로 **엑셀을 원본으로 두고, 올리면 DB를 그 엑셀에 맞춘다**(`psd/sync.py`).
화면에서 한 건씩 입력하는 기능은 없다 — 원본이 둘이 되면 다음 업로드 때 헷갈리기 때문이다. 잘못 적은
기록은 엑셀에서 고치거나 지운 뒤 다시 올린다.

1. "교체 기록" 탭에서 엑셀을 고르고 **비교하기**를 누른다. 아직 저장하지 않는다.
2. 지금 기록과 비교한 결과가 나온다: **새 기록 · 고친 기록**(같은 역·문·날짜인데 사유나 부품이 다름)
   **· 엑셀에 없는 기록 · 그대로**. 반영하면 교체주기·예정일이 어떻게 바뀌는지도 함께 나온다.
3. **반영하기**를 누르면 저장하고 업로드 이력에 한 줄 남긴다. "올리는 사람"을 적으면 이력에 같이 남는다(로그인이 없어 확인은 안 함).

운영은 현장 엑셀에 계속 적고 한 달에 한 번(급한 교체가 있었으면 그때) 누적 파일을 통째로 올리는 방식을 권한다.

- **같은 파일을 다시 올려도 기록이 늘지 않는다**("바뀌는 기록이 없습니다"). 매달 누적 파일을 올려도 된다.
- **비교 범위**는 파일에 나온 역들의, 파일의 가장 이른 날짜 ~ 가장 늦은 날짜 사이다. 누적 파일이면 전체,
  한 달·한 역 파일이면 그 달·그 역하고만 비교하고 범위 밖 기록은 건드리지 않는다. 비교 결과에 범위 양 끝이
  엑셀 몇 행인지 나온다 — 한 달 파일에 옛날 정정 한 줄이 섞여 범위가 넓어진 경우를 찾을 수 있다.
- **엑셀에 없는 기록은 기본으로 지우지 않는다.** 엑셀에서 지운 기록이 맞을 때만 "이 N건을 지웁니다"를 체크한다.
  20건이 넘으면 다른 파일을 고른 건 아닌지 경고한다.
- 엑셀 안에 똑같은 줄이 두 번 있으면 한 번만 넣고, DB에 같은 기록이 두 번 있으면 하나만 남긴다.
- **업로드 이력**에서 되돌릴 수 있다. 나중 업로드가 앞 업로드의 기록을 또 고쳤을 수 있어서, 가장 최근
  업로드부터 차례로만 되돌린다. 새로고침하거나 다음 날이 되어도 된다.
- "전체 기록 엑셀로 받기"는 DB의 기록을 업로드 양식 그대로 내려받는다. 원본 엑셀을 잃어버렸을 때 이 파일을
  이어 쓰면 되고, 그대로 다시 올리면 "변경 없음"이 나온다.

**양식은 코레일 "승강장안전문 장애 이력 관리 현황" 그대로다**(2026-11-24 v3, `psd/excel_io.py` 상단 설명). 현장이 쓰는 파일을
그대로 올리면 "고장현황 전체" 시트에서 머리글 줄(양식은 12행)을 찾아 그 아래를 읽고, 수식만 깔린 빈 줄과 동해선이 아닌 줄은 건너뛴다.

- 꼭 있어야 하는 칸: 년도·월·일, 역, 장애인지, 장애부위②(소분류), 조치사항. 문마다 있는 소분류는 승강장 선로(예: `상본선(#3)`)와
  출입문(예: `2-1`)도 있어야 한다. 나머지 칸(장애내용·고장원인·조치 상세·접수자·완료일 …)은 비워도 되고, 있으면 그대로 저장한다.
- 장애인지: 사후조치(신고받고 출동) = 고장, 사전조치(점검 중 발견·예방) = 예방. 교체주기 계산에선 사후조치만 수명 끝으로 센다.
- 조치사항: 교체(주요 부품) · 단순교체(부속 부품) · 수리 · 조정 · 리셋 · 기타. 설치일(새 수명 시작)은 교체 때만 바뀐다.
  장애형태(장애/보수/예방보수)는 조치사항으로 정해진다 — 규칙과 다르게 적혀 있으면 받되 경고로 알려 준다.
- 기록에 처음 나온 부본선(상부본선·하부본선)은 그 선로의 문 16개와 부품을 자동으로 만든다. 본부·PSD설치·설치년도·업체 칸은 역 정보로 저장한다.
- 소분류 이름은 띄어쓰기·쉼표·괄호 차이를 무시하고 분류표와 맞춘다. 분류표에 없는 소분류, 날짜·역·장애인지·조치사항 오류,
  문 단위인데 선로·출입문이 없는 줄은 받지 않는다(한 줄이라도 틀리면 전체를 저장하지 않는다 — all-or-nothing). 미래 날짜와 그 역의
  PSD 사용개시일보다 앞선 날짜(연도 오타 등)도 받지 않는다.
- "빈 양식 내려받기"의 첫 시트 "고장현황 전체"는 머리글만 있고, 예시는 둘째 시트 "작성 예시"에 있어 지우지 않고 올려도 들어가지 않는다.

API로도 같다(`delete_missing=true`는 엑셀에 없는 기록도 지움):

```bash
curl -F "file=@정비기록.xlsx" http://127.0.0.1:8000/api/replacement-records/compare   # 비교만
curl -F "file=@정비기록.xlsx" http://127.0.0.1:8000/api/replacement-records/sync      # 반영
```

올린 기록은 예정일뿐 아니라 교체주기에도 반영된다(`psd/calibrate.py`): 날씨 공식 값을 사전값으로 두고, 와이블 수명 분포를
베이지안으로 보정한다. 형상모수 β, 공식 치우침 κ, 역 사이 흩어짐 τ는 소분류마다 전 역 기록으로 함께 추정하고(계층 모델),
수리·조정·리셋·기타는 나이 그대로, 단순교체는 절반, 교체는 새것으로 본다(가정, 가상 나이). **날씨 공식이 없는 소분류는 기준 10년을
약하게만 믿어**(κ 사전분포를 넓게) 기록 쪽으로 빨리 옮겨 간다. 주기의 80% 범위도 내고, 예정일도 이 범위로 "80% 범위 시작~끝"을
함께 보여 준다. 숨은 정답과 비교하려면 `python scripts/check_calibration.py`(2026-11-24 더미: 기본값 대비 오차 62% → 보정 15.5%,
80% 범위 적중 85%). 계산이 10년을 넘어도 예정일에는 제조사 권장 10년까지만 쓴다.

## 반복 고장 의심 문

같은 문에서 고장이 되풀이되면 부품만 바꿔서는 안 끝나는 문(설치·정렬·주변 환경) 문제일 수 있어 따로 보여 준다(`psd/repeat.py`, `GET /api/repeat-doors`).
고장 건수만 보면 더미 기록에서 문 736개 중 387개(53%)가 "2건 이상"이라 쓸모가 없어서, **같은 역 다른 문들의 평균과 비교**한다.

- 최근 3년 고장 기록(사유 "고장"만, 한 기록 = 1건)을 문마다 센다. 종합제어반(역 공통)은 뺀다.
- 같은 역 다른 문의 평균 건수로 포아송 분포를 두고, 그 평균이라면 이 문이 이만큼 이상 나올 확률이 1% 미만이고 3건 이상이면 표시한다.
- 같은 역끼리만 비교해서, 역 전체가 날씨 탓에 고장이 잦은 경우(교체주기 보정이 맡음)와 그 문만 유난한 경우를 나눈다.
- 2026-11-03 더미 기록 기준으로 안락 북울산 방면 1-1, 태화강 부전 방면 2-2 두 곳이 걸린다.

화면: 상태색(빨강·노랑·회색·초록)과 겹치지 않는 보라색 "↻ 반복"으로 표시한다 — 현황 오른쪽 맨 위 카드, 노선도의 역 점 옆 표시, 역 목록·역 화면 왼쪽 목록의 "↻ 반복 N", 역 요약 상자, 문 그림의 보라 테두리와 보라 문 번호("↻ 1-1"), 문 칸에 고장 건수·같은 역 평균·고장 부품. 카드·상자는 배경 없이 왼쪽 보라 줄로만 구분한다(색이 많아 강조를 낮춤).

## AI 고장 위험도

`psd/risk.py`, `GET /api/risk`. 교체주기(`psd/calibrate.py`)가 역 x 부품 종류마다 주기 하나를 낸다면, 이 모델은 **문·부품 하나하나의
"앞으로 6개월 안 고장 확률"** 을 낸다. 수리를 거듭한 부품이나 고장이 잦은 문을 위로 올린다.

- 학습 데이터: 매달 1일마다 부품마다 그 전 기록만으로 특징(부품 종류, 날씨 공식 주기, 마지막 전체 교체 뒤 경과, 가상 나이, 고장 수,
  같은 문 최근 고장, 역 고장률, 달)을 만들고, 정답은 그 뒤 6개월 안 고장 여부. 약 20만 행.
- 모델: scikit-learn 그래디언트 부스팅(`HistGradientBoostingClassifier`).
- 검증: 마지막 6개월치 스냅샷을 숨기고 그보다 앞선 기록으로만 학습해 맞혀 본다. 2026-11-16 더미 기준 상위 100개 중 실제 고장 11.7%
  (평균 3.7%의 3.2배, "수명 사용 비율 순"은 4.5%), AUC 0.627. 숨은 정답을 아는 모델도 AUC 0.644·상위 100개 13.2%라 고장이
  대부분 우연인 데이터에서 거의 끝까지 따라간 셈이다.
- **더미 데이터로 학습한 점수다.** 실제 현장 성능은 실제 기록이 와야 안다.
- **사전 학습 모델(데스크탑)은 벌마다 숨은 정답을 바꿔 학습한다**(2026-11-26). 정답이 하나면 그 세계의 소분류별 고장률을 외워
  다른 정답에서 AUC 0.763 → 0.609(기준 방법 0.596)로 떨어졌다. 섞어 학습하면 본 적 없는 정답에서 0.695다
  (`scripts/check_truth_transfer.py`, `데스크탑_작업_안내.md` 3장).
- 화면: 현황 오른쪽 "AI 고장 위험도 상위", 부품 상세의 "AI 고장 위험도"(확률·순위·근거), AI 관리 탭(위험도 순위·버전·검증·학습 이력·다시 학습).

**재학습 흐름** (`psd/risk.py` `retrain`, `GET /api/risk-models`, `POST /api/risk-models/retrain`)

1. 정비기록 반영·되돌리기가 끝나면 뒤에서 새 모델(도전자)을 학습한다(30초 안팎, 한 번에 하나). 기록이 지난 학습과 같으면 건너뛴다.
2. 지금 쓰는 모델(챔피언)이 학습 때 못 본 최근 기간(정답이 다 보이는 달, 최대 6개월)을 검증 기간으로 잡는다. 도전자는 그 기간보다
   6개월 이상 앞선 기록으로만 학습한 판으로, 챔피언은 그대로 둘 다 맞혀 본다.
3. 도전자 AUC가 챔피언보다 0.005 넘게 낮지 않고, 기준 방법(수명 사용 비율 순)보다 나으면 바꾼다. 아니면 "보류"로 남기고 지금 모델을 쓴다.
4. 업로드를 되돌려 지금 모델이 없어진 기록까지 보고 학습한 상태면, 그 모델은 겨룰 상대에서 빼고 새로 세운다.
5. 버전마다 학습일·계기·기록 범위·검증 점수·결과·이유를 `risk_models`에 남기고, 모델 파일은 `models/risk_v{번호}.joblib`.

테스트(`pytest`)는 업로드 때 재학습하지 않게 `PSD_AUTO_RETRAIN=0`으로 돈다(`tests/conftest.py`).

**가상 현장** (`python scripts/virtual_field.py`, v3에선 소분류가 많아 데스크탑에서 돌린다 — `데스크탑_작업_안내.md`): 실데이터가 없어 숨은 정답이 있는 시뮬레이터로 2022~2028년 기록을 만들고,
분기마다 그날까지의 기록만으로 주기를 다시 보정·위험도 모델을 다시 학습해, 숨은 정답과 그 뒤 실제 고장으로 채점한다(시나리오 4개).
결과는 `data/processed/virtual_field.csv`, 화면은 AI 관리 탭 아래 그래프. v2(부품 7종) 결과는 v3와 맞지 않아 2026-11-25에 지웠다 —
데스크탑에서 다시 돌리기 전까지 그래프 자리에 "결과가 없습니다"가 나온다. v2 때 요약(공식이 30% 틀렸으면 기록 2~3년에 주기 오차가 절반,
위험도 모델은 기록 1년 반부터 기준 방법보다 나음)은 `데이터셋_v2_설계.md` 10장.

## 보고서 출력

- 엑셀: `GET /api/report`(전체 역) 또는 `GET /api/report?station_id=1`(역 하나)
- PDF: `GET /api/report.pdf`(운영 중인 역 전부를 역 순서로 묶음, 몇 초 걸림) 또는 `GET /api/stations/{역 번호}/report.pdf`(역 하나, A4 2쪽)

보고서는 받는 사람이 "어느 안전문의 무엇을 · 몇 개 · 언제까지" 바꿔야 하는지 바로 보이게 짰다(2026-11-02, 계산은 `psd/report_common.py`).

| | 엑셀(`psd/report_excel.py`) | PDF(`psd/report_pdf.py`) |
| --- | --- | --- |
| 한눈에 | "요약" 시트: 상태별 개수 | 1쪽 위: 상태별 개수 + 다음 교체(부품·개수·날짜·남은 기간) |
| 교체 작업 | "교체 작업" 시트: 1년 안 교체할 것(+ 확인 필요)을 부품·예정일별로 묶고 대상 안전문 나열, 완료일·비고 칸 | 1. 교체 작업 목록(같은 내용, 완료일 칸) |
| 자재 주문 | "요약" 시트: 부품 x 6개월 안 / 6개월~1년 / 1년 안 합계 / 1~2년 / 확인 필요 / 지난 1년 고장(예비품 참고). 전체 역이면 "역별 주문" 시트도 | 2. 자재 주문 수량(같은 표) |
| 부품별 | "전체 부품" 시트: 부품 하나하나(다음 교체일·남은 기간·교체주기·마지막 교체일) — 거르기용 | 3. 부품별 다음 교체, 2쪽: 안전문별 예정일 표·최근 교체 이력 6건 |

주문 수량은 예정 교체만 센다. 돌발 고장은 언제 날지 몰라, 예비품은 "지난 1년 고장"(고장으로 바꾼 개수)을 참고한다.

화면에서는 현황(범위·형식 선택)과 역 화면(그 역, 형식 선택)의 "보고서 내려받기"에서 받는다.

## 테스트

```bash
python -m pytest tests/ -v
```

`tests/test_cycle.py`는 설계 문서 손계산 예시와 계산의 기본 성질(AWS 지점별 묶음 포함)을,
`tests/test_status.py`는 경고 상태(빨강·노랑·초록·확인 필요 — 화면 이름은 교체 임박·주의·안전·확인 필요) 판정 규칙을, `tests/test_excel_io.py`는
엑셀 업로드 파싱을, `tests/test_sync.py`는 엑셀과 DB 기록 비교(새 기록·고친 기록·빠진 기록·중복)를,
`tests/test_calibrate.py`는 고장 기록으로 주기를 보정하는 계산을, `tests/test_repeat.py`는 반복 고장 문 판정을,
`tests/test_taxonomy.py`는 분류표 읽기를 검증한다. 테스트는 예시 분류표에도 있는 소분류 코드만 써서 분류표 파일이 없어도 돈다.
`tests/test_api.py`만 예외로 **실제 MySQL DB가 필요하다**(설치 5단계까지 해 둔 DB).
